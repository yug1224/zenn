## Type-Aware が Stable になった

https://oxc.rs/docs/guide/usage/linter/type-aware

リポジトリルートの `oxlint.config.ts` で、`typeAware` と `typeCheck` をオンにしています。`typeAware` は lint が型を見るスイッチです。未処理の Promise のような、見た目だけでは分からないものがここで落ちます。Alpha のときの記事で入れたのが、これです。

https://zenn.dev/dress_code/articles/d655cd7a43b936

`typeCheck` は、同じ TypeScript program からコンパイラ診断も Oxlint 経由で出すスイッチです。lint の結果と型エラーが一度に並ぶので、手元では `tsc` を別待ちする感覚が薄くなります。

これらの設定が、次の Lefthook からも読まれます。

```ts
export default defineConfig({
  options: {
    // Type-Aware Linting Stable（oxlint-tsgolint@7）
    typeAware: true,
    // 早期検知用。フルの型検査の正は pnpm typecheck
    typeCheck: true,
    reportUnusedDisableDirectives: 'error',
  },
});
```

Type-Aware のガイドには、CI の `tsc --noEmit` を Oxlint 側の型チェックに寄せられると書いてあります。用途は Lefthook と手元の早期検知です。

:::message
早期検知は oxlint の `options.typeCheck` です。フルチェック（PR の CI の正）は、今も各アプリの TypeScript 7 の `tsc`（`pnpm typecheck`）です。PR Check の typecheck ジョブは外していません。
:::

### フルの typecheck を待たずに、ステージしたファイルの型は分かる

pre-commit は Lefthook です。ステージした `src` 配下の `.ts` / `.tsx` だけを oxlint に渡しています。

```yml
# lefthook.yml（構成を簡略化した例）
lint:
  glob: 'src/**/*.{ts,tsx}'
  exclude:
    - '**/schema.d.ts'
    - '**/routeTree.gen.ts'
  run: pnpm oxlint --tsconfig ./tsconfig.json --fix --fix-suggestions {staged_files}
```

型を壊した `src` 配下の `.tsx` を `git add` して `git commit` すると、Lefthook の `lint` が oxlint を回したところで止まり、コミットは作られません。フルの `pnpm typecheck` はここでは走っていません。

止まるのはステージした `.ts` / `.tsx` の lint と、そのファイルに返ってきた `options.typeCheck` の診断です。ステージしていないファイルの型エラーでは、このフックは止まりません。

## React Compiler の lint を分割した

Oxc の React Compiler Support に合わせ、oxlint を 1.79.0 へ上げました。公式は Compiler 由来のルールを 22 本に増やし、旧 nursery の単一ルール `react/react-compiler` はカテゴリ別へ置き換える、と書いています。私たちは、この分割ルールへ移しています。

annotation の記事では、jsPlugin で `eslint-plugin-react-hooks` を読んでいました。ビルド側の annotation は、あのときから変えていません。jsPlugin 自体は hooks の recommended を読むために残し、Compiler 由来の lint だけ oxlint の `react/*` 分割ルールへ移しています。

https://zenn.dev/dress_code/articles/92dfb9206f50f3

公式 Getting Started の `categories.correctness: "error"` は採っていません。correctness 相当は 12 本あり、壊れると困る 11 本だけ個別に error にしました。

外した 1 本が `react/incompatible-library` です。TanStack Table の `useReactTable` のように、ライブラリ側が Compiler と相性の悪い API を出している箇所で、このルールだけが大量に鳴るためです。

restriction / suspicious / perf も明示的に off です。このうち `react/unsupported-syntax` はカテゴリは restriction ですが、公式では recommended です。構文面の制限が強く出るので、recommended でも載せていません。

| 扱い                                   | ルール                                                                                                                                                                                                                                                           |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| error                                  | `react/error-boundaries`, `react/globals`, `react/immutability`, `react/preserve-manual-memoization`, `react/purity`, `react/refs`, `react/set-state-in-effect`, `react/set-state-in-render`, `react/static-components`, `react/use-memo`, `react/void-use-memo` |
| off（公式 correctness だが外した）     | `react/incompatible-library`                                                                                                                                                                                                                                     |
| off（restriction / suspicious / perf） | `react/unsupported-syntax`, `react/invariant`, `react/rule-suppression`, `react/syntax`, `react/todo`, `react/capitalized-calls`, `react/exhaustive-effect-dependencies`, `react/hooks`, `react/memo-dependencies`, `react/no-deriving-state-in-effects`         |

載せる形は、次のような抜粋です。表の名前を `rules` に落としたものです。

```ts
plugins: ['react'],
rules: {
  'react/error-boundaries': 'error',
  'react/globals': 'error',
  'react/immutability': 'error',
  'react/preserve-manual-memoization': 'error',
  'react/purity': 'error',
  'react/refs': 'error',
  'react/set-state-in-effect': 'error',
  'react/set-state-in-render': 'error',
  'react/static-components': 'error',
  'react/use-memo': 'error',
  'react/void-use-memo': 'error',
  'react/incompatible-library': 'off',
  'react/unsupported-syntax': 'off',
  // restriction / suspicious / perf の残りも off
},
```

`'use no memo'` を付けた Table まわりのファイルを、分割ルールのまま流しても、ディレクティブ由来の診断は出ませんでした。ソースを読んだ確認ではなく、自社の対象ファイルを流した観測です。TanStack Table まわりのオプトアウトは、これまでどおり babel 側に残しています。公式ブログはルール一覧と旧 `react/react-compiler` の置き換えを書いていて、`'use no memo'` の扱いまでは書いていません。

transform の `oxc-transform-react` は、まだ乗せていません。公式の preliminary benchmark では Babel より 10 倍速い、とのことですが、自社では測っていません。メインアプリは `@vitejs/plugin-react-swc` に `vite-plugin-babel` を足しているので、`@vitejs/plugin-react` への統合待ちをそのまま差し替える話でもありません。

lint の話はここまでです。型検査の正を oxlint に寄せない理由は、次の非対称です。

## TypeScript 7 への一本化はこれから

https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/

lint の `typeCheck` に一本化しなかったのは、速さの問題ではありません。見ているファイルの範囲が、まだ同じではないからです。

`schema.d.ts` と `routeTree.gen.ts` は `pnpm typecheck` の対象のまま、oxlint 側は `ignorePatterns` で外しています。生成物を lint するとノイズになるための非対称で、`typeCheck` を足しただけでは埋まりません。

tsgolint と TypeScript 7 の `tsc` は、出る診断がずれることもあります。私たちは `@tanstack/react-query` / `query-core` を 5.101.4 にピンしたうえで、そのずれを既知差分として扱っています。

ignore の非対称が残っているあいだは、PR の CI の正は `tsc` です。

型検査の正自体は、Alpha のときの記事で入れた tsgo（Native Preview）から、TypeScript 7 の `tsc` に置きました。プレビュー用の `@typescript/native-preview` は外しています。

ただし TypeScript 7.0 は programmatic API を同梱していません。`import 'typescript'` を利用するツールの peer 用に、ルートへ TypeScript 5.9.3 を残しています。ワークスペースの `typescript.tsdk` も、まだこちらを見ています。

エディタ向けには、[TypeScript 7 の公式拡張](https://marketplace.visualstudio.com/items?itemName=TypeScriptTeam.native-preview)も出ています。

ピンは 2026年8月時点です。`oxlint-tsgolint` の `7.0.2001` は、TypeScript 7.0.2 向け tsgolint のパッチ番号です。

| パッケージ      | バージョン | 置き場所                   |
| --------------- | ---------- | -------------------------- |
| oxlint          | `1.79.0`   | リポジトリルート           |
| oxlint-tsgolint | `7.0.2001` | リポジトリルート           |
| oxfmt           | `0.52.0`   | リポジトリルート           |
| TypeScript 7    | `7.0.2`    | 各アプリ                   |
| TypeScript 5    | `5.9.3`    | ルート（programmatic API） |

フロントエンドの PR Check で、成功した run を 12 本見ました。失敗 run は入れていません。数字はジョブ全体ではなく、本体ステップです。ピンと同じ 2026年8月時点の計測です。

`pnpm run lint:check` は `typeAware` と `typeCheck` 込みで 40秒前後（38〜44秒、多くは 39〜42秒）、型チェックの正の `pnpm typecheck` は 50秒前後（典型 46〜52秒）でした。typeCheck を足しても、lint が typecheck を飲み込むほどの差にはなっていません。一本化する判断は、この秒数より、見ている範囲と診断が揃うかの方が大きいと感じています。

## まとめ

Type-Aware を Stable に載せ、React Compiler の lint を分割ルールへ移しました。PR の CI の正は、今も `pnpm typecheck` です。

次は TypeScript 7 への一本化です。ignore の非対称と `query-core` まわりのずれを、運用で抱えてよいか。programmatic API 待ちで残している TypeScript 5 を、どこまで寄せられるか。揃ったと思えたら、CI の `pnpm typecheck` を外して、lint の `typeCheck` に寄せたいと考えています。transform は、そのあとでもよい、と思っています。

同じ規模で Type-Aware Stable や React Compiler の lint、TypeScript 7 を触っている人がいたら、X で [`@yug1224`](https://x.com/yug1224) まで教えてください。typeCheck を `tsc` の代わりにしているか、まだ並べているか、比較したいです。
